# doc2html

Конвертация документа — PDF, EPUB, XPS, MOBI, FB2, CBZ и всё остальное,
что открывает [PyMuPDF](https://pymupdf.readthedocs.io/) — в читаемый
HTML, Markdown или обычный текст (UTF-8), с сохранением картинок.

Скрипт называется `doc2html.py` (раньше был `pdf2html.py` — сохранено
переименование через `git mv`, история не потеряна). PDF остаётся
основным и наиболее протестированным форматом — детекция врезок через
векторную графику и приём для сломанных кодировок опираются именно на
PDF-специфичные возможности PyMuPDF; для других форматов конвейер тот
же самый (он универсален по конструкции), но специально протестирован
пока только на PDF и на растровом изображении (как one-page документ).

Решает типичные проблемы «наивных» конвертеров:

- **Кодировки.** Текст извлекается через PyMuPDF, нормализуется (`NFKC`)
  и очищается от «мусорных» символов Private Use Area. Если у документа
  сломана ToUnicode-таблица шрифта (текстовый слой в принципе
  нечитаем — глифы маппятся в управляющие символы, а не в буквы),
  скрипт это автоматически детектирует и распознаёт такую страницу
  через офлайн-OCR (EasyOCR, ru+en) вместо битого текстового слоя.
  Результат всегда валидный UTF-8.
- **Картинки.** Встроенные изображения рендерятся в исходном виде (с
  учётом ориентации/трансформаций — иначе картинка может выйти
  перевёрнутой или зеркальной) и сохраняются в подпапку `images/`.
- **Колонтитулы.** Короткий текст в верхних/нижних ~9% страницы
  (номер страницы, название главы) распознаётся как колонтитул,
  выносится в отдельную маленькую строку `.page-meta` вместо середины
  абзаца — и, если название главы/раздела повторяется на нескольких
  страницах подряд без изменений, показывается только один раз (номер
  страницы при этом показывается всегда).
- **Заголовки.** Заголовки разделов распознаются и выделяются (`<h2>`/
  `<h3>` в HTML, `##`/`###` в Markdown) — на чистом текстовом слое по
  размеру шрифта относительно основного текста страницы, при OCR по
  высоте строки относительно медианной. Работает независимо от того,
  какой из двух путей извлечения сработал на конкретной странице.
- **Многоколоночная вёрстка (HTML).** Если страница по геометрии
  PDF-блоков действительно разбита на две колонки (см. ниже), в HTML
  они рендерятся рядом друг с другом (`<div class="cols">`), а не одним
  сплошным потоком — на мобильных экранах колонки складываются
  вертикально. Markdown/txt всегда остаются линейным текстом (колонка
  за колонкой), поскольку для них порядок чтения важнее визуального
  сходства со страницей.
- **Несколько форматов вывода.** `--out-format html|md|txt`. Каждая
  страница распознаётся и извлекается **один раз**, в промежуточное
  представление (JSON в служебной папке состояния); рендер в
  конкретный формат делается из него отдельно, так что смена
  `--out-format` на уже готовых страницах не требует повторного OCR.
- **Диапазон страниц, потоковый вывод, продолжение прерванной
  конвертации.** Результат пересобирается после каждой обработанной
  страницы — файл можно открыть прямо во время работы скрипта.
  Повторный запуск с теми же (или другими) параметрами `-o`/файла
  автоматически пропускает уже готовые страницы.

## Установка

Требуется установленный conda (Miniconda/Anaconda) и PowerShell.

```powershell
.\install.ps1
```

Если PowerShell блокирует запуск скриптов ("cannot be loaded because
running scripts is disabled"), один раз разрешите их для своего
пользователя:

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

Создаст conda-окружение **`pdf2html`** (имя окружения оставлено как
есть для обратной совместимости с уже установленным — переименование
означало бы переустановку тяжёлых пакетов типа torch/easyocr на
несколько ГБ; если хотите переименовать и его, самый дешёвый способ —
`conda create -n doc2html --clone pdf2html`, затем
`conda env remove -n pdf2html`, это копирует уже скачанные пакеты, а
не качает их заново) и поставит базовые зависимости из
`requirements.txt` (PyMuPDF, Pillow, torch, easyocr) — их достаточно
для конвертации без подписей (по умолчанию) или с
`--generate-alt lmstudio`. Модель EasyOCR (ru+en, ~100 МБ) скачается
один раз при первом обращении.

Офлайн-бэкенд подписей `--generate-alt blip` требует пакет
`transformers` — он **не ставится по умолчанию** (это отдельная
зависимость только под BLIP, ничего больше от неё не зависит).
Поставить его можно двумя способами:

```powershell
# Сразу при установке
.\install.ps1 -WithBlip

# Или потом, в уже созданное окружение
conda run -n pdf2html python -m pip install -r requirements-blip.txt
```

Сами веса модели BLIP (~1 ГБ) скачаются один раз при первом реальном
вызове `--generate-alt blip`.

## Активация окружения

Скрипт нужно **дот-сорсить** (запустить с ведущей точкой и пробелом),
иначе активация останется только внутри скрипта и не подействует на
текущую сессию PowerShell:

```powershell
. .\activate.ps1
```

## Использование

```powershell
python doc2html.py input\example.pdf -o output
```

### Параметры

| Параметр | По умолчанию | Описание |
|---|---|---|
| `input_file` | — | Путь к исходному файлу: PDF, EPUB, XPS, MOBI, FB2, CBZ, изображение и т.п. (обязательный) |
| `-o`, `--output-dir` | `output` | Папка для результата |
| `--out-format {html,md,txt}` | `html` | Формат результата |
| `--save-images` / `--no-save-images` | включено | Сохранять картинки в `<output>/images` |
| `--generate-alt {off,blip,lmstudio}` | `off` | Описание картинок: не генерировать / офлайн BLIP / локальный сервер LM Studio |
| `--start-page N` | 1 | Первая страница для конвертации (1-индексация) |
| `--end-page N` | последняя | Последняя страница, включительно |
| `--restart` | выкл | Игнорировать сохранённое состояние (в запрошенном диапазоне) и начать заново |
| `--clean-state` / `--no-clean-state` | **включено** | Удалять папку состояния, когда весь документ будет готов целиком |
| `--gpu` / `--no-gpu` | автоопределение | Использовать GPU (CUDA) для OCR/BLIP |
| `--lmstudio-url` | `http://localhost:1234/v1` | Адрес сервера LM Studio |
| `--lmstudio-model` | `lfm2.5-vl-450m` | Имя vision-модели в LM Studio (используется при `--generate-alt lmstudio`) |

### Поведение флагов сохранения картинок

По умолчанию (`--save-images`, `--generate-alt off`): картинка
сохраняется (`<img>` в HTML, `![]()` в Markdown), но alt/подпись
пустая — самый быстрый режим, никакая модель не запускается и не
скачивается.

- `--save-images` (вкл) + `--generate-alt blip|lmstudio`: картинка
  сохраняется с содержательным описанием.
- `--save-images` (вкл) + `--generate-alt off` (по умолчанию):
  картинка сохраняется, но без описания.
- `--no-save-images` + `--generate-alt blip|lmstudio`: картинка не
  сохраняется, вместо неё в текст вставляется `[Изображение: <описание>]`.
- `--no-save-images` + `--generate-alt off`: картинка не сохраняется,
  вместо неё — заглушка `[Изображение]`.

В **txt** картинки всегда описываются текстом (`[Изображение: ...]`
или `[Изображение]`), файлы при этом всё равно сохраняются на диск,
если `--save-images` включён — просто в plain-текст встроить их
некуда.

### Диапазон страниц, несколько форматов, потоковый вывод и продолжение

```powershell
# Только первые 50 страниц
python doc2html.py input\book.pdf -o output --end-page 50

# Продолжить с 51-й - готовые 1-50 не трогаются, просто дописываются
python doc2html.py input\book.pdf -o output --start-page 51

# Тот же диапазон, но в Markdown - страницы уже извлечены, повторного
# OCR не будет, отработает за секунды
python doc2html.py input\book.pdf -o output --end-page 50 --out-format md
```

- После каждой обработанной страницы итоговый файл переписывается
  целиком (атомарно) — можно открывать и обновлять прямо по ходу
  работы скрипта.
- Если скрипт прервать (Ctrl+C, сбой, перезагрузка) и запустить снова
  с той же папкой `-o`, он сам найдёт уже готовые страницы и продолжит
  с места остановки — конвертировать заново не нужно.
- Диапазон страниц в повторном запуске может отличаться от первого —
  так можно скармливать документ по частям вручную.
- `--out-format` можно менять между запусками свободно — рендер идёт
  из уже извлечённых страниц, а не заново распознаёт документ. Имя
  результирующего файла зависит от формата (`book.html`/`book.md`/
  `book.txt`), так что разные форматы не перезаписывают друг друга.
- Если между запусками поменять `--save-images`/`--generate-alt`,
  скрипт не станет молча продолжать по-новому: выведет предупреждение
  (эти флаги меняют содержимое ещё не обработанных страниц) и
  попросит либо `--restart`, либо новую папку `-o`, если нужно
  пересчитать уже готовые страницы новыми настройками.
- `--restart` пересчитывает **только запрошенный диапазон** — страницы
  вне `--start-page`/`--end-page` не трогаются.

#### Служебная папка состояния

Промежуточные фрагменты страниц лежат в скрытой папке рядом с
результатом: `output\.<имя файла>.doc2html-state\pages\0001.json`,
`0002.json`, ... Каждый файл — это извлечённое содержимое страницы в
формате, независимом от `--out-format` (список абзацев/картинок/
колонтитулов/врезок); сами картинки там не дублируются, они только в
`output\images\`, фрагмент лишь ссылается на файл по имени.

По умолчанию папка состояния **удаляется автоматически**
(`--clean-state`), но только когда **весь** документ (не только
запрошенный в этом запуске диапазон) полностью готов — если что-то
вне диапазона ещё не сконвертировано, скрипт выведет об этом
сообщение и папку не тронет. Отключить автоудаление — `--no-clean-state`
(например, если планируете позже перерендерить страницы в другой
`--out-format` и не хотите терять кеш раньше времени). Удалить папку
состояния вручную можно в любой момент — потеря картинок ей не
грозит, только возможность возобновить/дозаконвертировать без
пересчёта.

### GPU и LM Studio

`--gpu`/`--no-gpu` включает CUDA-ускорение для EasyOCR и BLIP через
`torch.cuda` — работает только с NVIDIA-картами. **Если видеокарта не
NVIDIA (например Intel Arc/Iris Xe с OpenVINO), этот флаг не поможет**
— PyTorch на CPU-сборке CUDA не увидит независимо от флага.

В этом случае для подписей к картинкам можно использовать локальный
сервер **LM Studio** с vision-моделью — многие раннтаймы LM Studio
умеют ускоряться на GPU разных производителей, не только NVIDIA:

1. В LM Studio загрузите vision-модель (принимающую изображение на
   вход) и включите Local Server (по умолчанию `http://localhost:1234`).
   По умолчанию скрипт рассчитывает на **`LiquidAI/LFM2.5-VL-450M-GGUF`**
   (id модели в LM Studio: `lfm2.5-vl-450m`) — компактная (450M) и
   быстрая vision-модель, которую стоит держать загруженной именно под
   эту задачу. Можно использовать любую другую (`Qwen2-VL`, `InternVL`
   и т.п.) через `--lmstudio-model`.
2. Запустите конвертацию с этим бэкендом:

```powershell
python doc2html.py input\book.pdf -o output --generate-alt lmstudio
```

Если сервер недоступен или модель не найдена, скрипт сразу
останавливается с понятной ошибкой (со списком доступных в LM Studio
моделей), не тратя время на конвертацию текста впустую.

**OCR намеренно не переведён на LLM/LM Studio.** Для дословного
распознавания текста документа офлайн-OCR (EasyOCR) — правильный
инструмент: языковая модель для этой задачи рискует незаметно
перефразировать или «додумать» текст, что для оцифровки недопустимо.
LM Studio используется только там, где приблизительное, творческое
описание уместно и полезно — для подписей к картинкам.

### Пример

```powershell
. .\activate.ps1
python doc2html.py "input\Веб-дизайн книга Якоба Нильсена.pdf" -o output
```

Результат: `output\Веб-дизайн книга Якоба Нильсена.html` и, если
включено сохранение картинок, `output\images\*.png`.

## Как восстанавливается макет при OCR

Когда текстовый слой документа сломан, текст страницы полностью
распознаётся через OCR (EasyOCR), а не берётся из исходного файла.
Дальше он проходит через собственную реконструкцию макета (не
встроенную группировку EasyOCR), специально написанную для типичных
проблем такого распознавания:

- **Оглавления и указатели.** Детектор текста часто видит запись вида
  «Название ....... 27» как ДВА отдельных блока (разреженный пунктирный
  разделитель не распознаётся как текст) — но оба блока занимают почти
  одну и ту же высоту строки. Строки объединяются по проценту
  вертикального перекрытия боксов (а не по позиции по X), поэтому
  название и номер корректно склеиваются в одну запись «Название 27»,
  сколько бы пунктирная линия между ними ни весила по ширине.
- **Перенос слов через дефис** ("бо-\nлее" → "более") исправляется
  автоматически.
- **Врезки/выноски на полях** (текст в рамке сбоку от основной колонки,
  на той же высоте страницы) находятся не по расположению OCR-текста
  (у некоторых книг боковые врезки специально выровнены по общей сетке
  строк с основной колонкой, поэтому по высоте их не отличить), а по
  собственной векторной графике документа — рамка/заливка врезки.
  Такая область закрашивается перед основным OCR-проходом (как и
  картинки) и распознаётся отдельно, целиком, а результат оформляется
  отдельным блоком (`<aside class="callout">` в HTML, цитата `>` в
  Markdown, отступ в txt) после основного текста страницы — вместо
  того чтобы дробить и вклинивать её построчно в середину предложений
  основной колонки. Если у вёрстки конкретного документа врезки
  визуально никак не выделены (ни рамки, ни заливки) — этот механизм
  их не найдёт, они по-прежнему могут попасть в основной поток.
- Изображения перед OCR закрашиваются, чтобы текст интерфейса/надписи
  на скриншотах не попадал в основной текст как «шум»; рамка вокруг
  самого изображения (если есть) не принимается за отдельную врезку.
- **Колонтитулы** (короткий текст в верхних/нижних ~9% страницы)
  выносятся из общего потока в `.page-meta`; если margin-абзац на
  самом деле склеил номер страницы и название раздела в одну строку
  («8 Содержание») — они перед этим разделяются, чтобы дедупликация
  повторов (см. выше) срабатывала независимо от того, какой именно
  номер страницы в этот раз оказался рядом с названием.
- Изредка (пример на титульных данных: ISBN) короткий текст с обилием
  цифр всё ещё может по ошибке получить класс `.ocr-numbers` (блёкло-
  серым, курсивом) — эвристика не бьёт по смыслу, а лишь по доле цифр
  в тексте.
- **Настоящие две колонки** (не врезка, а просто текст, набранный в две
  колонки на одной странице) определяются по геометрии PDF-блоков: если
  блоки чётко группируются в левую и правую группы одинаковой высоты
  (не просто с разным отступом — реальный параллелизм проверяется
  отдельно, иначе титульная/выходные данные с разной шириной абзацев
  ошибочно принимаются за две колонки), между ними ищется настоящий
  пустой промежуток («gutter»), и OCR-строки, чей внутренний разрыв
  попадает точно в этот промежуток, разбиваются по нему — даже если сам
  промежуток на странице узкий (несколько пунктов). Это тот же
  промежуток, что используется для бокового рендеринга в HTML (см.
  выше); вложенные подпункты внутри одной колонки (например,
  под-темы одного пункта оглавления) при этом получают визуальный
  отступ (`margin-left`) пропорционально их собственному сдвигу от
  начала колонки — это не настоящий `<ul>`/`<li>`, а лишь визуальное
  приближение к вложенности, которого обычно достаточно, чтобы список
  не превращался в сплошную стену текста.
- Как и любая эвристика, это не идеально: изредка короткая вставка
  (например, скобочная ремарка-отсылка к рисунку на соседней странице),
  которая на исходной странице расположена близко по высоте к обеим
  колонкам сразу, может остаться слегка не на своём месте в тексте —
  но, в отличие от прежнего поведения, слова внутри самого предложения
  при этом больше не разрываются посередине.

## Примечания

- Описания картинок через BLIP генерируются на английском языке;
  через LM Studio — на языке, который выберет загруженная модель
  (зависит от промпта и самой модели).
- Первый запуск с `--generate-alt blip|lmstudio`/OCR будет заметно
  медленнее из-за загрузки весов моделей; при повторных запусках
  модели берутся из локального кеша.
- Для больших документов (сотни страниц) OCR и генерация подписей —
