# doc2html

Конвертация PDF/EPUB/XPS/MOBI/FB2/CBZ/изображений (всё, что открывает
PyMuPDF) в HTML/Markdown/txt с сохранением картинок. Подробности —
[readme.md](readme.md). Единственный рабочий файл — `doc2html.py`.

## Тестирование при разработке

- Реальные книги лежат в `input/` (не коммитятся, см. `.gitignore`).
- `conda run -n doc2html python ...` иногда падает на Windows с
  `UnicodeEncodeError`/`CONDA_NO_PLUGINS` при выводе кириллицы — надёжнее
  звать интерпретатор окружения напрямую:
  `C:\Users\Lopat\miniconda3\envs\doc2html\python.exe doc2html.py ...`
  (и `export PYTHONIOENCODING=utf-8` в Bash-сессии).
- **После любой правки формата/схемы блоков — гонять
  `tests/regression_check.py`** тем же интерпретатором окружения, что и
  выше (`C:\Users\Lopat\miniconda3\envs\doc2html\python.exe
  tests\regression_check.py`, не голый `python` — иначе можно случайно
  попасть на системный интерпретатор без нужных пакетов). Запускает
  реальную конвертацию (с OCR, где нужно) конкретных страниц 4 книг из
  `input/` и проверяет структуру JSON — каждая проверка привязана к
  конкретному найденному и исправленному багу (колонки, заголовки,
  врезки, таблицы, код-блоки, списки, курсив/ссылки/сноски, позиция
  картинок). Каждый чек пропускается сам, если соответствующей книги нет
  локально.
- Для разовой ручной проверки конкретной страницы —
  `--start-page N --end-page N --restart --no-clean-state
  --generate-alt off` в отдельную scratch-папку `-o`, не в реальный
  `output/` пользователя.

## Бэклог форматирования (по приоритету)

Источник — аудит 4 книг из `input/` + постраничная проверка 12 случайных
страниц против оригинала (агенты реально гоняли `page.find_tables()`,
`get_links()`, разбирали флаги спанов — не предположения). Полный отчёт с
цитатами и номерами страниц: см. историю сессии (артефакт «Аудит
форматирования — doc2html»).

- [x] **Таблицы.** `page.find_tables()` + очистка шумных колонок
  (`clean_table_rows`/`_merge_split_columns`) + исключение случая, когда
  листинг кода с колонкой номеров строк ошибочно распознаётся как таблица
  (`_region_is_actually_code`, переиспользуется и для врезок — см. ниже).
  Тип блока `"table"`.
- [x] **Блоки кода/листинги.** Детект по моноширинному шрифту
  (`is_monospace_font_name`) или по соседству с подписью «Лістинг/Листинг
  N.N» (`LISTING_CAPTION_RE`). Тип блока `"code"`, `<pre><code>` с
  сохранением отступов и переносов строк (не через `extract_block_text`).
- [x] **Списки (частично).** Маркер (►•‣▪●○◦ или `N.`/`N)`) → тип блока
  `"li"`, группировка соседних в `<ul>/<ol>` при рендере. Плюс разбиение
  ОДНОГО PDF-блока, слипшего несколько пунктов (`split_block_into_list_items`
  — кейс Non-Designers стр. 284, где 7 пунктов были одним блоком).
  **Не решено**: обратный кейс, когда пункт списка и его перенесённая
  строка/следующий абзац оказываются в РАЗНЫХ соседних PDF-блоках
  (Konovalenko стр. 6 — маркер «► ...» отрывается от своего продолжения,
  а последний пункт списка слипается со следующим несвязанным абзацем).
  Это требует reflow-логики поверх границ PDF-блоков (аналогично тому, что
  уже есть для OCR-пути в `reflow_rows_into_paragraphs`) — сознательно не
  делал в этом заходе, риск регрессий на обычной прозе выше пользы.
- [x] **Курсив/полужирный внутри абзаца.** Span-level `"runs"` на блоке
  (`extract_block_runs`/`block_emphasis_runs`) — по флагам (`flags&2`
  italic, `flags&16` bold) прогоны оборачиваются в `<em>`/`<strong>`
  (`*`/`**` в Markdown) вместо плоской склейки текста. Только для
  «чистого» пути (на OCR-страницах шрифтовых флагов физически нет).
- [x] **Ссылки.** `find_page_links` (`page.get_links()`) даёт реальные
  href через ту же систему `"runs"`: внешние → `<a href>`/mailto:,
  внутренние (GOTO) → якорь на `#page-N` (работающее оглавление). Плюс
  `linkify_html`/`linkify_markdown` — regex-автолинковка голых URL в уже
  извлечённом тексте на РЕНДЕРЕ, работает для обоих путей извлечения (в
  т.ч. OCR, раз не требует PDF-объекта ссылки).
- [x] **Верхние индексы + баг сносок.** `flags&1` → `"superscript"` в
  `"runs"` → `<sup>`. Отдельно: `collect_superscript_digit_markers` +
  `FOOTNOTE_MARKER_RE` — сноска, чей номер совпадает с реальным
  superscript-маркером на странице, больше не уходит в `margin`
  (был баг на Konovalenko стр. 16).
- [x] **Безрамочные врезки + `find_callout_boxes` в «чистом» пути.**
  `find_callout_boxes` теперь используется и в non-OCR-пути (не только
  OCR-fallback), плюс `NOTE_LABEL_RE` — текстовый триггер по метке
  («ПРИМЕЧАНИЕ»/«ВНИМАНИЕ»/«СОВЕТ») как альтернатива рамке (кейс
  ci_sharp). Обе врезочные проверки прогоняются через
  `_region_is_actually_code`, чтобы не поглотить блок кода с рамкой
  (регрессия, пойманная и исправленная в этом же заходе на Konovalenko
  стр. 90 — рамка листинга геометрически неотличима от врезки).

Весь бэклог из аудита реализован. Единственное сознательно оставленное
ограничение — кросс-блочное слияние/разрыв пункта списка (см. выше).

## Архитектурные фиксы (не из аудита, из ревью CodeRabbit)

- [x] **Позиция картинок.** Раньше все картинки страницы дописывались в
  конец `blocks` одним отдельным проходом после основного текста — рвало
  связь картинки с её подписью и абзацем. Теперь картинка обрабатывается
  прямо в основном цикле (non-OCR путь) или сливается по `y0`/колонке с
  уже собранными абзацами через `_merge_flow_entries` (OCR путь — нужно
  учитывать, в какой колонке лежит картинка, иначе плоская сортировка по
  `y0` перемешает левую и правую колонку). `ocr_page_regions` теперь
  возвращает ещё и `gutter`, чтобы `extract_page_blocks` мог определить
  колонку картинки.
- [x] **`assemble_output` на каждой странице — O(n²).** Пересборка и
  перезапись всего файла результата после каждой обработанной страницы
  (ради потокового вывода) на большой книге давала квадратичный рост
  работы. Теперь `ASSEMBLE_EVERY_N_PAGES = 10` — пересборка раз в 10
  страниц (плюс гарантированно после самой первой страницы захода, чтобы
  не казалось, что конвертация зависла) — финальная пересборка после
  цикла осталась как есть, гарантирует полный файл в конце независимо от
  троттлинга.

Отдельно (не баг, для контекста): OCR-точность на «Нильсене» — все 3
случайные OCR-страницы дали серьёзные проблемы (путаница букв о↔o, в↔B,
склейки слов) — это потолок точности EasyOCR на этом шрифте, не ошибка
вёрстки/сегментации. Не в этом бэклоге.

- [x] **Картинки разных книг перезаписывали друг друга в общем `-o`.**
  `images_dir` была одной общей `<output>/images/` папкой на весь `-o`, а
  имя файла картинки — только `image_{page:04d}_{index:04d}.png`, без
  привязки к книге. При конвертации двух разных книг в одну `-o`-папку
  картинка книги B на том же номере страницы+индексе молча перезаписывала
  файл книги A — а уже готовый JSON книги A продолжал на него ссылаться,
  так что в её HTML отображалась чужая картинка. Фикс — `images_dir =
  output_dir / "images" / input_path.stem`, отдельная подпапка на каждую
  книгу; `src` в блоке картинки теперь `images/<книга>/<файл>`.

- [x] **Гиперссылки .docx полностью терялись.** `page.get_links()`
  для страниц, полученных PyMuPDF из `.docx` (reflow в
  PDF-подобное представление), всегда пуст — Word не хранит ссылки
  как аннотации страницы, поэтому `find_page_links` в принципе не может
  их найти, в отличие от настоящего PDF. На реальном резюме пользователя
  все 20 гиперссылок (mailto, tel, LinkedIn, 17 ссылок на GitHub-проекты)
  молча пропадали, включая случаи вроде «linkedin.com/in/lopatnov» —
  голого текста без `http://`/`www.`, который вдобавок не ловит и
  `BARE_URL_RE`. Фикс — `extract_docx_hyperlinks` читает
  `word/document.xml` + `word/_rels/document.xml.rels` напрямую из zip
  (не через PyMuPDF), затем `apply_known_hyperlinks` находит точные
  вхождения текста ссылки в уже извлечённых блоках и проставляет `href`
  в существующий механизм `"runs"` (расщепляя, а не затирая, уже
  найденные bold/italic-прогоны). Специфично для `.docx` — на PDF
  `extract_docx_hyperlinks` возвращает `{}` и ничего не меняет.

- [x] **Двухколоночная врезка рассыпалась в кашу.** `ocr_page_regions`
  OCRит каждую `callout_boxes`-врезку как ОДНУ недифференцированную
  область без учёта колонок - если врезка сама по себе внутренне
  двухколоночная (независимо от того, сколько колонок на самой странице -
  дизайнерское решение врезки, а не страницы), текст обеих колонок
  перемешивался построчно в бессмыслицу (Нильсен стр. 42 - «Замените свой
  монитор...»). Фикс - `detect_callout_column_boundary_x` (тот же
  геометрический поиск гутера, что и `detect_column_boundary_x` для
  основного потока, но ограниченный блоками внутри конкретной врезки, с
  исключением её собственного широкого заголовка через
  `CALLOUT_TITLE_WIDTH_RATIO` и сниженным минимумом блоков - у врезки их
  объективно меньше, чем у всей страницы). Найдено и подтверждено на
  реальной боевой конвертации пользователя, не в аудите/бэклоге.

## Детерминированный аудитор (`tools/audit_pages.py`)

Read-only скрипт: сверяет уже сконвертированный JSON с независимо
извлечённым текстом страницы (точный текстовый слой либо свежий OCR-
проход) по покрытию словами и порядку чтения — без LLM в контуре, см.
докстринг файла. Три бага выше найдены им же на реальной книге
пользователя. Известное ограничение: сигнал "order" ненадёжен на
подлинно двухколоночных страницах, поскольку сырой порядок из EasyOCR
`readtext` сам по себе не учитывает колонки (перемежает лево/право по
высоте) — это ограничение самого аудитора, а не обязательно баг в
`doc2html.py`, проверять такие находки нужно вручную рендером страницы.
